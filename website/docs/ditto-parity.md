PocketRun 的第 1—11 章把一套本机 Android AI 助手的骨架搭了出来，但这只是起点——**我们的最终目标，是在保持这套本机执行架构的前提下，逐步覆盖 Ditto 整体背后的核心能力，同时用清晰可读的教程把每一层原理讲透。**

固定 Demo、最小 BusyBox/musl、三个固定工具和两步模型任务都是循序渐进的教学阶段，绝不是最终的功能上限。这一页如实记录当前做到哪一步、还差什么，以及哪些原产品行为仍需要进一步取证。

## 当前进度：已经建好的底座（第 1—11 章）

- **Android 控制通道**：App 自有无线 ADB → UID 2000 独立 `app_process` → typed Binder（AIDL）→ 后端持有的 720×1280 隔离 `VirtualDisplay`、共享内存截图、有界 UI 树和定向输入。
- **Linux 与终端通道**：普通 App UID 私有工作目录 → `ProcessBuilder` 管道 → 基于 `nativeLibraryDir` + PRoot 的最小 Alpine（BusyBox/musl）→ 基于 JNI `/dev/ptmx` 的真实交互式 PTY。
- **工具与模型编排**：带严格 Schema 校验、目标绑定、一次性手机审批和可证明清理的 `TaskHost` → 内存单任务账本 `SingleTaskContext` → 基于 Anthropic Java SDK 的有界 `AgentLoop`。

## 已知的 Ditto 静态对照依据

我们在对齐原产品时坚持**只认直接证据、不凭猜测编造**的原则。目前关于 Ditto 的已知静态事实主要来自此前对 **Ditto 0.1.14 APK** 的有限分析：

- 同样采用将 PRoot 与 loader 打包进 `nativeLibraryDir` 的方式来满足 Android 可执行限制，并带有 Termux 风格的 JNI/PTY 路径。
- APK 内携带有 Alpine 3.24.3（515 个归档条目）以及 `apk` 包管理工具。
- 该次反编译重建（JADX 1.5.1）存在 32 处错误，不能凭空补猜缺失方法；公开仓库 [`ditto-termux-packages`](https://github.com/WindySha/ditto-termux-packages) 也尚未核实为完整 App 源码或对应版本。

因此，下表中未经过直接证实的原产品行为，都会明确标为“待核实”。

## 能力缺口与演进清单

| 能力维度 | PocketRun 当前状态（第 1—11 章） | 差距与后续推进方向 |
| --- | --- | --- |
| **Linux 用户态分发** | Alpine 3.22.8 派生的最小 BusyBox/musl（4 个 ELF、2 个代码绑定） | 显著小于完整 rootfs 范围；需按实际任务需求补齐常用工具、动态库和目录结构，并同步维护对应源码与开源许可 |
| **包管理能力** | 暂不含 `apk`、软件源与动态装包入口 | 需先核实目标产品真实的装包、更新、网络与持久化流程，并在遵守 Android W^X 限制的前提下实现 |
| **Agent 工具集** | 仅开放设备信息、固定 CSV 行数、受限虚拟屏 3 个固定工具 | 固定 CSV 只是教学探针，并非通用文件与命令工具；需在守住审批与沙箱边界的前提下扩充通用工具协议 |
| **Android 通用 App 操作** | 仅针对固定 Demo 页完成截图、UI 树、点击与可打印 ASCII 输入 | 尚未覆盖一般第三方 App 的启动、复杂控件选择、滚动导航、中文输入与授权边界 |
| **终端交互界面** | 真实 PTY 后端 + React 64 KiB 纯文本预览 | 尚不具备 ANSI 颜色、光标定位和全屏 TUI 程序渲染能力；需按目标体验决定是否接入完整终端渲染组件 |
| **完整跨能力闭环** | 显示操作、文件命令、手机审批和两步模型任务已分别跑通 | “读 `items.csv` → 整理数据 → 填进目标 App → 保存 `result.txt`”的完整跨通道任务将在后续章节串联并验证故障恢复 |
| **模型视觉与界面观察** | 仅向模型发送极小的文本白名单摘要（不传截图或原始 UI 文本） | 尚未建立向多模态模型传递截图与脱敏 UI 树的安全观察协议，需结合隐私与防提示词注入边界设计 |
| **持久化、恢复与记忆** | 任务账本仍在当前进程内存；第 12 章已实现用户可查看/纠正/删除的加密笔记，明确选中后用于模型任务并已实际验收 | 记忆不等于运行恢复。任务持久化、防重复副作用和中断后核对属于第 13 章；当前无自动学习/向量检索，原产品对应行为继续取证 |
| **设备与 OEM 兼容** | 已在 API 36 ARM64 专用环境验证核心路径 | 尚未覆盖广泛 Android 版本与各品牌 OEM 定制系统的兼容分支和降级策略 |

:::note 关于 MCP、Subagent、多任务与大规模 Eval
目前本地并没有直接证据表明 Ditto 原产品内置了 MCP、产品级 Subagent、并发多任务或大规模评测体系。这些属于通用的 Agent 演进方向，不会混算进“Ditto 已有功能对照”；若未来引入，会单独标明来源和设计动机。
:::

## 后续章节与验收原则

**第 12 章（用户可管理的记忆）已通过实际任务验收并推进发布**；下一步推进 **第 13 章（完整跨能力任务与故障恢复）**。当完整能力清单明确后，也会自然扩展更多章节，不受当前编号限制。

无论后续功能如何扩充，全书始终守住三条不变的验收标准：
1. **逐项对齐**：每个新能力明确记录“预期协议 → PocketRun 实现入口 → 真实场景验证 → 剩余边界”。
2. **不放宽底线**：从 Demo 演进到通用工具时，绝不放松 UID 边界、正数 `displayId` 隔离、手机端审批和可证明清理约束。
3. **写给人看**：每一项新增能力的原理和工程权衡，都会同步写成清晰、自洽的教程章节。
