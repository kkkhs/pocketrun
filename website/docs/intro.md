## 成果目标

我们要逐步构建一个 Android 应用：用户提出任务，Agent 在明确授权范围内观察界面、操作测试 App、读写工作目录并执行命令，最后返回可检查的结果。

例如，在自己的测试设备上打开一个演示 App，完成一次表单操作，并把执行记录保存到应用工作目录。每一步都应能解释：**谁发起调用、在哪个进程执行、持有什么权限、怎样判断成功、如何停止。**

当前仓库只有教程站工程和三篇学习材料，**Android 应用尚未实现**。本阶段先建立可靠的写作、构建和发布流程，设备能力随后逐章实现与验收。

## 为什么从边界开始

熟悉 React / TypeScript，意味着你已经会组织组件、管理状态、处理异步调用。这些经验能迁移到 React Native UI，但 Android 的执行模型需要补上几块知识：

- React Native 的界面元素不是浏览器 DOM；原生模块调用也不是一次普通的网页请求。
- UI 状态、Agent 决策、Android 系统操作和 Linux 命令执行属于不同职责。
- 普通应用 UID 与 ADB shell 身份不同；把一次调用跨过桥接层，并不会自动增加权限。
- “发送了命令”不等于“完成了任务”。必须检查输出、实际界面和失败状态。

先读[系统概览](architecture.md)，再做[第 0 章](chapter-0.md)的工程实践。这样后续不会把所有逻辑塞进一个聊天组件。

## 分步准备

### 1. 网站阶段需要的工具

- Git：会创建分支、查看 diff、提交和处理 PR。
- Node **24.18.0** 与 npm：本仓库通过 `.nvmrc` 固定 Node 版本。
- 编辑器与浏览器：编辑 Markdown，检查生产预览。
- GitHub 账号：只有发布到自己仓库时需要；纯本地阅读与构建无需登录。

### 2. 未来应用章节需要的基础

能读懂 TypeScript 类型、`async` / `await` 和 React 组件；知道命令的标准输入、标准输出、退出码是什么。Kotlin、JNI、Binder 和 PTY 会在用到时解释，不要求现在全部掌握。

Android Studio、Android SDK Platform Tools 与对应 Android / React Native 版本所需的 JDK，将在应用工程章节锁定版本。此阶段不需要安装或构建 Android 应用。

### 3. 未来设备章节的前提

准备一台**自己拥有或明确获授权的 Android 11 及以上、ARM64 设备**，以及可恢复的测试数据。涉及 ADB 时，必须由设备使用者开启调试并确认授权；无线调试还需要按系统流程配对。设备品牌、系统版本和后台限制需要单独记录。

不要求 root。后续会区分普通应用与 shell 的能力，遇到系统拒绝应记录限制，而不是把权限失败当作需要绕开的障碍。

## 每章如何实践

每章使用相同的节奏：

1. **成果目标**：先定义本章结束时能看到什么。
2. **为什么这样做**：从已有 React / TypeScript 经验解释新的调用链与边界。
3. **分步实现**：一次只引入当前需要的能力。
4. **预期与验证**：给出运行命令、可观察结果与通过条件。
5. **排错**：把权限、连接、构建和业务失败分开定位。
6. **练习与小结**：自己做一个变化，再确认最小检查能发现错误。

验证记录要写明执行环境和结果。没有运行的步骤标为待验证；真实设备结果不能用桌面预览替代。

## 预期与验证

现在你应能说清楚两件事：仓库当前交付的是教程站；最终学习目标是一个有明确权限与可验证结果的 Android AI 助手。

接下来完成第 0 章，在本地打开课程导读、系统概览和工程章节，检查导航、深链刷新与代码块。这是本阶段能够实际执行的检查；设备运行与首次线上发布仍是各自独立的验收项。

## 常见困惑

- **会 React，为什么还需要 Kotlin？** UI 可以用 TypeScript，但 Android 生命周期和系统能力需要原生层承接。
- **Agent 是否直接拥有设备权限？** 不。Agent 提出工具调用，由执行层检查参数、授权、范围和设备状态。
- **是否现在就选择模型或 Agent 宿主？** 不。先确定工具契约和执行边界，后续再依据实测决定模型接入与宿主位置。

## 练习与小结

写下一个只操作自己测试数据的任务，并拆成“观察 → 操作 → 验证”三步。为每一步补上失败时的停止条件，再到系统概览判断它应属于哪一层。

记住本课程的主线：**先让每个执行步骤可信，再让 Agent 把步骤串起来。**
