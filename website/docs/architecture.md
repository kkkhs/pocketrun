## 成果目标

本篇先建立一张职责地图：React Native / TypeScript 负责 UI 与任务编排；Kotlin 承接 Android 生命周期和原生调用；经用户授权启动的 shell 后端承担其身份允许的系统操作；应用内命令环境承担工作目录与 CLI 会话。

这是后续实现的设计路线，**不是已经完成的应用架构**。每条跨进程链路都要在实现章节验证，尤其是不同系统版本和设备上的权限差异。

## 为什么要分层

可以把 React Native UI 理解为已有 React 经验的延伸：组件展示任务状态，事件触发异步操作，结果再更新界面。但执行层与网页不同——它跨越 Android 进程、Binder 和原生资源，不能只用一个 `Promise` 的成功返回来判断完成。

| 层 | 拥有什么 | 不应承担什么 |
| --- | --- | --- |
| React Native / TypeScript UI | 用户输入、任务状态、确认与结果展示 | 在组件里直接拼接任意系统命令 |
| Agent 与工具策略 | 任务上下文、工具定义、参数与范围检查 | 把模型输出当作权限授予 |
| Kotlin / 必要时 JNI | Android 生命周期、原生模块、会话与资源句柄 | 假设调用桥接后就变成 shell 或 root |
| shell 后端 | 授权 ADB 启动后获得的 shell 身份与 Binder 服务 | 把全部系统接口开放给任意调用者 |
| 应用内命令环境 | 普通应用身份下的进程、工作目录和输入输出 | 读取其他应用私有数据或改变 Android 权限 |

权限策略必须由开发者控制的执行代码落实。模型可以建议动作，但不能取消授权检查，也不能自行扩大工具范围。

## 分步追踪一次调用

### 1. 从 UI 到受约束的工具调用

用户确认任务后，UI 把任务交给 Agent。Agent 提出一个结构化工具调用，例如读取工作目录里的文件，或者在一个指定显示上执行测试动作。

执行层先检查工具名、参数类型、允许的路径或目标、设备状态及用户确认。有效调用才进入原生层；无效调用返回明确错误。删除文件、提交表单等有副作用的步骤还需要与风险相称的确认。

### 2. 普通应用：Kotlin、JNI 与生命周期

安装后的 PocketRun 是一个普通 Android 应用，持有 Android 分配的应用 UID。React Native 原生模块把 TypeScript 请求交给 Kotlin；需要 PTY 等原生能力时再通过 JNI 调用相应代码。

Activity 重建、应用切后台和进程退出都可能影响会话。会话状态不能只存在于组件里；原生层需要明确谁持有连接、谁负责取消，以及什么时候释放进程、文件描述符和显示资源。JNI 是语言边界，不是权限提升机制。

### 3. 经授权的 ADB：启动 shell 后端

未来章节会在自己拥有或获授权的设备上，通过 ADB 启动一个独立后端进程。在普通量产设备的常见调试环境中，`adb shell` 以 **shell UID 2000** 运行，而不是应用 UID，也不是 root。具体身份和可用操作必须在设备上检查。

该后端可以通过 Binder 向应用提供一组受限制的能力。调用链是：**普通应用 → Binder 请求 → shell 后端校验调用 → 后端执行 → 结构化结果**。

后端应校验调用者身份、会话授权、操作白名单和参数。Binder 本身不自动证明调用者可信；也不会把客户端应用永久变成 shell。后端执行仍受 Android 权限检查、SELinux、系统版本和设备策略限制。连接失效或设备重启后，需要重新确认后端是否存在和是否获授权。

### 4. VirtualDisplay：目标显示与资源

VirtualDisplay 是 Android 的虚拟显示对象，内容绘制到调用者提供的 `Surface`。它有对应的 `Display` 和 `displayId`，后续操作必须明确针对哪个显示，不能默认所有动作都落在主屏上。

要分别验证创建显示、获得画面、启动测试 Activity、输入操作与释放资源。**创建一个 VirtualDisplay，并不自动获得任意 App 的启动、画面读取或输入注入权限。** 不同显示标志、调用身份、系统接口与应用适配会影响结果；需要系统能力的操作由经授权且有对应权限的后端执行，不能承诺所有设备通用。

`displayId` 是运行期句柄，不应写死或在显示销毁后继续使用。显示释放会移除其窗口；进程终止时也会自动释放虚拟显示。正常结束仍应主动释放显示及由自己持有的 `Surface`。

### 5. 命令执行：先管道，需要交互时再用 PTY

对于一次性、非交互命令，Kotlin 的 `ProcessBuilder` 管道足够：传入参数列表，消费 stdout / stderr，检查退出码，并处理超时与取消。持续输出时必须及时消费两个输出流，避免进程因管道缓冲区写满而卡住。

交互式 shell、终端编辑器或依赖 `isatty` 的程序需要 **PTY（伪终端）**。它提供终端语义、尺寸与交互输入；输出可能带控制序列，且通常不再像两条独立管道那样区分 stdout 和 stderr。PTY 会话还需要关闭文件描述符、取消子进程和处理窗口尺寸变化。

不要一开始就把所有命令做成终端：用管道完成当前任务，遇到真实的终端交互需求再增加 PTY。

### 6. Linux 用户态：PRoot + Alpine 与 Termux

未来命令环境有两类路线需要比较：

- **PRoot + Alpine**：在应用可访问的目录中组织 Linux 用户态文件系统，用 PRoot 的用户态机制处理路径等兼容需求。它不是启动了一套新的 Linux 内核，也不是虚拟机；可运行的软件仍受设备 ABI、系统调用与用户态兼容性限制。
- **Termux 路线**：采用适配 Android 环境的工具与包。它的二进制、库和目录假设与 Alpine 并不相同，不能把两套包当作可直接互换的环境。后续选择复用方式时还需检查官方支持方式与许可证。

无论哪条路线，在普通应用内启动的进程仍受该应用的 Android UID 和沙箱约束。环境中看到的模拟 root 身份或 `fakeroot` 元数据，只影响用户态看到的行为；不会获得内核 root、额外 SELinux 权限或其他应用的数据访问权。

命令环境与 shell 后端是两条不同执行路径。应用工作目录里的 CLI 不应为了方便自动转发到 shell；需要系统操作时使用明确命名、受约束的后端工具。

## Agent 宿主：留到实测再决定

TypeScript 适合描述工具契约，但这不意味着桌面 Node 工具可以原封不动放进 React Native JavaScript 运行时。

Agent 是否需要单独的 Node 进程、是否运行在应用内 Linux 用户态，以及是否存在远端宿主，**当前未定**。后续应根据依赖是否要求 Node API、设备 ABI、启动成本、网络与凭据边界、进程恢复方式来选择。本阶段不增加 Node Agent 运行时或模型 SDK。

确定宿主前，先把工具的请求、结果、取消和失败语义设计清楚。这样迁移决策层位置时，不必改变权限边界。

## 预期与验证

后续每条链路至少应留下一个可运行的检查：

| 检查对象 | 预期可观察结果 | 必须覆盖的失败 |
| --- | --- | --- |
| 普通应用与 shell 身份 | 分别记录真实进程 UID 和调用路径 | 后端未启动、授权失效或身份不符 |
| Binder 工具 | 允许的调用返回结构化结果 | 未授权调用者或越界参数被拒绝 |
| VirtualDisplay | 当前句柄、目标显示与画面对应 | 显示销毁、目标不支持或操作被拒绝 |
| 管道与 PTY | 输出、退出状态、交互行为可区分 | 大量输出、取消和资源泄漏 |
| Agent 调用 | 执行结果回到 UI，可停止任务 | 无效参数、危险操作未确认或重复执行 |

这些是应用章节的验收目标，本阶段没有连接设备执行它们。可先完成[第 0 章](chapter-0.md)的网站工程检查。

## 排错：按边界定位

- **UI 有响应但原生没有结果**：检查模块调用、原生日志和取消状态，再看跨进程连接。
- **权限被拒绝**：先确认实际执行进程的 UID 与允许范围，不用反复改模型提示词。
- **显示存在但测试 App 不工作**：分别检查显示配置、启动结果、应用适配和目标 `displayId`。
- **命令一直不结束**：区分程序等待交互、输出流未消费和进程取消失败。
- **应用切后台后任务中断**：检查 Activity / 服务 / 后端各自的生命周期，避免用重试掩盖重复副作用。

需要用户可感知的持续任务时，可以评估前台服务及其可见通知，但**前台服务不是进程永生机制**。后台启动、服务类型、系统超时、用户停止和设备策略仍需处理；重启后的恢复还要重新建立授权与会话。

## 练习与小结

把“在测试 App 中填写表单”和“在工作目录执行一次文件转换”分别写成调用链。标出每一步的执行身份、输入校验与验证结果，再考虑用户中途停止时哪些资源需要释放。

本篇最重要的结论：**UI 展示状态，Agent 提出动作，执行层守住边界，实际结果决定任务是否完成。**
